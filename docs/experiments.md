# Эксперименты первого шага

Перед учебным запуском ученик формулирует прогноз и объясняет его. Это инструкция
воспроизведения; фактические проверки — в [verification.md](verification.md).
Проверка наставником не заменяет интерпретацию ученика.

## 1. Создание, повтор, статус

```bash
python3 scripts/demo.py
```

Сопоставить HTTP-коды, ID первого и повторного ответа, статус и остаток. Скрипт
проверяет контракт assertions. Разные запуски создают разные заказы: ключ каждый раз новый.

## 2. Данные и перезапуск процесса

Создать заказ, сохранить его ID, прочитать. Затем:

```bash
docker compose restart app
curl -i http://127.0.0.1:8080/health/ready
curl -i http://127.0.0.1:8080/orders/ORDER_ID
```

Пока приложение стартует, повторять проверку готовности. Зафиксировать отдельно
доступность процесса и сохранность данных. Дополнительный опыт: перезапустить
`postgres`, дождаться готовности и прочитать тот же ID. Том не удалять.

## 3. Отказ БД

```bash
docker compose stop postgres
curl -i --max-time 12 http://127.0.0.1:8080/health/live
curl -i --max-time 12 http://127.0.0.1:8080/health/ready
curl -i --max-time 12 http://127.0.0.1:8080/inventory/demo-item
docker compose logs --tail=30 app
docker compose start postgres
curl -i --max-time 12 http://127.0.0.1:8080/health/ready
```

После восстановления пулу может понадобиться время на соединение. Повторить ready,
записать время восстановления. Прерванную запись проверять по прежнему ключу:
ответ клиента сам по себе не определяет результат commit. В конце обязательно восстановить БД.

## 4. Конкурентные запросы

```bash
docker compose --env-file .env.example run --rm test pytest -q -p no:cacheprovider -k concurrent
```

Тесты работают только в отдельной БД. Изучить условия и assertions в `tests/test_orders.py`.
Это функциональная проверка конкуренции, не измерение максимальной пропускной способности.

Остановка экземпляра, дедлайн gRPC, пауза WAL и переподключение WebSocket будут добавлены
вместе с соответствующими компонентами.
