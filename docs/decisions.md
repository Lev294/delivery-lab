# Решения и ограничения

| Решение | Причина и цена |
| --- | --- |
| Один товар, одно количество, завершение заказа | Оставляем время на распределённые механизмы; нет оплаты, отмены и возвратов |
| Orders ×2 + Inventory | Разделяем масштабирование экземпляров и выделение сервиса; Inventory пока один |
| Одна БД, логическое владение таблицами | Экономия памяти и администрирования; общая роль и primary — общая точка отказа |
| SQL напрямую, без ORM | Видны условный UPDATE, UNIQUE и commit; SQL поддерживаем вручную |
| Три короткие транзакции + идемпотентный RPC | Переживаем повтор и потерю ответа; возможен зависший pending без повторного запроса |
| HAProxy с двумя режимами | Сравнение L4/L7 одним инструментом; сам proxy не дублируется |
| Асинхронная физическая реплика | Реальный WAL/recovery и задержка чтения; нет автоматического failover |
| WS-снимки + опрос primary | Работает между экземплярами без брокера; нагрузка растёт с подписчиками, истории событий нет |

## Настройки, влияющие на поведение

- gRPC deadline: `GRPC_TIMEOUT_SECONDS`, по умолчанию 1 с. `INVENTORY_DELAY_SECONDS`
  искусственно задерживает ответ **после commit**; используется только для опыта.
- gRPC reconnect: начальная пауза/минимальное окно подключения 200 мс, максимальная
  пауза 1 с, минимум между DNS-разрешениями 1 с. Это настройки локального стенда;
  они сокращают восстановление после пересоздания контейнера, но не убирают переходные ошибки.
- SQL-пул: 1–5 соединений на процесс/пул, очередь до 20, ожидание до 3 с.
  Orders имеет отдельные пулы primary и replica. connect timeout=3 с, statement timeout=3 с,
  lock timeout=2 с. Это пределы отдельных фаз, не общий HTTP-дедлайн.
- PostgreSQL Read Committed, условный UPDATE и CHECK неотрицательного остатка.
- Реплика: `wal_keep_size=256MB`, без replication slot и архива WAL. Долгий простой
  может потребовать новой base backup. Нельзя считать standby резервной копией:
  ошибочное удаление данных тоже реплицируется.
- HAProxy: connect 2 с, server 5 с, client 30 с, tunnel 1 час; healthcheck inter 1 с / fall 2.
  Долгое простаивающее WebSocket-соединение может закрыться по tunnel timeout, браузер переподключится.
- Образы закреплены digest, Python-пакеты — lock-файлом. Нужны плановые обновления безопасности.

## Восстановление реплики после потери WAL

Простой перезапуск primary обычно не требует пересоздания replica. При сообщении о
недоступном WAL сначала сохранить логи и убедиться, что primary здоров. Только затем
остановить и удалить **контейнер replica и её том**, создать replica заново через base backup.
Том primary не удалять. Имена томов зависят от Compose project; посмотреть `docker volume ls`
и `docker compose config --volumes` перед любыми ручными удалениями. Автоматического
опасного сброса скрипт реплики не делает.

## Безопасность и непокрытые гарантии

Стенд работает на localhost. Нет TLS/mTLS, авторизации, раздельных SQL-ролей бизнес-сервисов,
лимитов внешнего API, резервных копий и автоматического переключения primary. Пароли
генерируются локально и не публикуются; runtime-роль не superuser, но владеет таблицами.
Ключи идемпотентности без TTL и без привязки к пользователю. Тело успешного повтора содержит
текущее состояние заказа, а не байтовую копию первого ответа.

Один ноутбук, Docker VM, диск, proxy, Inventory и primary остаются точками отказа.
Проверки конкуренции — функциональные, не доказательство пропускной способности.
Остановка процесса не равнозначна отключению отдельного сервера или разделению сети.

Логи Orders содержат request_id, instance_id, путь, статус и длительность; Inventory —
order_id, outcome и признак replay. Сопоставлять бизнес-вызовы по order_id; полноценного
распределённого tracing пока нет. Пароли и тела запросов в прикладные логи не выводятся.
