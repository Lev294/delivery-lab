# Решения и ограничения

## 1. Маленькая предметная область

Один демонстрационный SKU `demo-item`, начальный остаток 100. Заказ содержит один SKU
и количество. Создание одновременно резервирует товар; статус становится `reserved`.
Единственный следующий статус — `completed`. Повтор завершения безопасен и не меняет
остаток. Отмена, оплата, доставка курьером, пользователи и интерфейс магазина вне объёма.

## 2. Сначала одна транзакция

Один процесс и одна БД позволяют получить проверяемый исходный вариант. PostgreSQL
атомарно сохраняет заказ и уменьшает доступный остаток. Вместо отдельного чтения
остатка с последующим безусловным обновлением используем условный `UPDATE`.
Проверка `CHECK (available >= 0)` — дополнительное ограничение в БД.

Используется стандартный уровень изоляции PostgreSQL Read Committed. Конкурирующий
`UPDATE` одной строки ждёт изменяющую её транзакцию, затем повторно проверяет условие
на актуальной версии строки. Это свойство конкретного запроса, а не обещание, что
произвольная последовательность SELECT/UPDATE безопасна при Read Committed.
[Документация PostgreSQL](https://www.postgresql.org/docs/17/transaction-iso.html).

## 3. Идемпотентность создания

Клиент присылает UUID в `Idempotency-Key`. На уровне БД ключ уникален. Первый успешный
запрос создаёт заказ (201), повтор того же тела возвращает текущее состояние того же
заказа (200). Повтор ключа с другими SKU/количеством — 409. Это не кеш исходного HTTP-ответа:
если заказ уже завершён, повтор создания вернёт `completed`.

Неуспешный резерв откатывает заказ и ключ: после пополнения допустим повтор того же тела.
Ключи хранятся без TTL; авторизации и разделения ключей по пользователям пока нет.
Новый ключ означает новое намерение создать заказ. Сеть не даёт гарантии «ответ доставлен
ровно один раз», даже когда бизнес-операция защищена от повторного эффекта.

## 4. SQL напрямую и небольшой пул

Psycopg выбран вместо ORM: запросы короткие, SQL и границы транзакции видны в коде.
Цена — преобразования и SQL поддерживаем вручную. Соединения выдаёт пул: 1–5 соединений
на процесс, ожидание до 3 с, очередь до 20 ожидающих; соединение проверяется перед выдачей.
Таймаут установки соединения 3 с, SQL-команды 3 с, ожидания блокировки 2 с.
Это пределы отдельных фаз, не общий HTTP-дедлайн в 3 с.

Контекст соединения делает commit при нормальном выходе и rollback при исключении.
[Документация Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/pool.html).

## 5. Запуск и миграции

Compose ждёт готовности БД, выполняет SQL-миграции и запускает API. Миграции учитываются
в `schema_migrations`, конкурентный запуск защищён advisory lock. Применённые файлы
нельзя редактировать: добавлять следующий номер. Автоматического downgrade и проверки
контрольных сумм пока нет. Healthcheck не является автоматическим переключением на запасной узел.
[Порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/).

PostgreSQL сохраняет данные в именованном томе. `.env` создаётся локально с отдельными
случайными паролями администратора и приложения; в Git и контекст сборки он не попадает.
Приложение работает отдельной ролью без superuser, но эта роль пока также выполняет
миграции и владеет таблицами. Разделение migration/runtime ролей отложено.

Инициализационный скрипт роли выполняется только для пустого тома. Изменение `.env`
само по себе не меняет пароль существующей роли. Полная очистка тома удаляет данные.
[Официальный образ PostgreSQL](https://hub.docker.com/_/postgres).

## 6. Границы достоверности и безопасности

Это локальный демонстрационный стенд. Нет TLS, авторизации, резервного копирования, автоматического
failover, ограничителя частоты и управления секретами промышленного уровня. HTTP-порт
слушает только 127.0.0.1; публиковать его в интернет не предусмотрено.
Один компьютер, Docker VM и диск остаются общей точкой отказа будущих экземпляров.

Логи содержат request ID, instance ID, метод, путь, статус и длительность; тела запросов,
пароли и строки подключения не пишутся. Для внешнего использования потребуется также
пересмотр допустимых полей логирования. Ответы внутренних ошибок БД не раскрывают SQL.

Версии Python-зависимостей закреплены lock-файлом, базовые Docker-образы — digest.
Это обеспечивает повторяемость артефактов, но не заменяет регулярного обновления версий.
